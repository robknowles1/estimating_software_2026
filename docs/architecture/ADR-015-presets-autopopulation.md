# ADR-015: Product Presets Auto-Population — Data Model, Two-Level Indirection, and Workflow Design

**Status:** proposed
**Date:** 2026-05-27

Related: ADR-010 (per-estimate materials price book), ADR-011 (EstimateMaterialsController design), SPEC-022 (material alias auto-population)

---

## Context

### What the Excel spreadsheet actually does

Blake's spreadsheet has two tabs that work together as a complete estimating system:

**Tab 2 — Material Costs (the per-estimate price book).** Before estimating, Blake enters every raw material for the specific job: sheet goods (`PL1`–`PL6`, MEL variants), hardware (hinges, pulls, slides, banding options) with that job's supplier-quoted prices. A short code (`PL1`) maps to a job-specific material. This is modeled correctly by `estimate_materials` with `short_code` added by SPEC-022.

**Tab 1 (Presets tab) — Product type defaults.** Every product type (e.g., "Base 1 Door") has a full row of defaults:
- Exterior qty + exterior TYPE code (e.g., `0.22`, `3/4" MEL G2S`)
- Interior qty + interior TYPE code (e.g., `0.22`, `1/4" MEL`)
- Back TYPE code
- Banding TYPE code (e.g., `BANDING3`)
- Draws qty
- Pulls qty + TYPE code (e.g., `1`, `PULL1`)
- Hinges qty + TYPE code (e.g., `2`, `HINGE1`)
- Slides qty + TYPE code (e.g., `1`, `SLIDE1`)
- Labor hours: detail, mill, assembly, finish, install (per-product-type)

When Blake adds any product row, ALL of these defaults auto-fill. This is why a 15-minute estimate is possible versus a full day. The "15-minute estimate" is almost entirely generated by the Presets tab.

### What the current data model captures

After SPEC-014 / ADR-010, the current `products` table correctly stores:
- `exterior_qty`, `interior_qty`, `interior2_qty`, `back_qty`, `drawers_qty`, `pulls_qty`, `hinges_qty`, `slides_qty`, `locks_qty`
- All six labor hour columns (`detail_hrs`, `mill_hrs`, `assembly_hrs`, `customs_hrs`, `finish_hrs`, `install_hrs`)
- `equipment_hrs`, `equipment_rate`, `other_material_cost`
- `unit`

`Product#apply_to(line_item)` copies all quantities and labor hours. Material FKs (`_material_id` on line_items) are left blank — the estimator must assign them from the estimate's price book.

### The gap that SPEC-022 and PR 41 expose

SPEC-022 added `short_code` to `estimate_materials` to link architect codes (like `PL1`) to materials. The service correctly auto-populates the four primary material FKs on CSV import by substring-matching the short code in the line item description.

**But this does not replicate the Presets tab.** The Presets tab provides TYPE codes — not just which short code matched a description substring, but which specific material code belongs in each individual slot of a given product type. The distinction:

- SPEC-022: "This line item description contains `PL1`, so all four primary slots get the PL1 estimate_material."
- Presets tab: "A Base 1 Door always uses `3/4" MEL G2S` for exterior, `1/4" MEL` for interior, no back, `BANDING3` for banding, `PULL1` for pulls, `HINGE1` for hinges."

These are different levels of specificity. SPEC-022 assigns the same material to all four primary slots. The Presets tab assigns specific, distinct materials per slot.

### The two-level indirection in the spreadsheet

The Excel design uses a two-level system:

**Level 1 — Job-specific price book (Tab 2):** Maps short codes to actual materials and prices.
- `PULL1` → "3" Satin Nickel Bar Pull, $4.50 each (this job)
- `HINGE1` → "Blum Compact 38N", $1.20 each (this job)
- `PL1` → "Maple Plywood 3/4"", $68/sheet (this job)

**Level 2 — Product type defaults (Presets tab):** Maps product types to slot TYPE codes.
- "Base 1 Door": exterior=`3/4" MEL G2S`, interior=`1/4" MEL`, banding=`BANDING3`, pulls=`PULL1`, hinges=`HINGE1`

When an estimate is built, the calculator reads Level 1 to resolve Level 2. A product knows it uses `PULL1`; the job knows `PULL1` costs $4.50. This separation is what makes the system repricing-safe.

In the current Rails app, Level 1 is `estimate_materials` (with `short_code`). Level 2 is partially present in the `products` table (qty defaults, labor hours) but has no equivalent for the TYPE codes — the slot-specific material code assignments.

### The non-CSV workflow gap

SPEC-022 only auto-populates material slots during CSV import or when "Apply short codes" is clicked. If Blake manually adds a line item by selecting a product from the dropdown, nothing auto-populates the material FK slots. He gets quantities and labor hours from `Product#apply_to`, but all `_material_id` columns are null. In the Excel model, adding a product row auto-fills everything from the Presets tab. The web app has no equivalent of this for manual entry.

### What PR 41 / SPEC-022 is and is not

PR 41 is correct and useful within its stated scope:
- The `short_code` field on `estimate_materials` is the right mechanism for Level 1 job-specific codes.
- Substring matching on description during CSV import is correct for the described workflow.
- The "Apply short codes" button is the right affordance for re-running matching after code changes.

PR 41 does NOT claim to solve the Presets gap. It solves the specific problem of auto-assigning materials when short codes appear in imported descriptions. It is a complete, correctly-scoped feature. The gap is that the product catalog lacks Level 2: slot-specific material code defaults per product type.

---

## Decision

**1. PR 41 / SPEC-022 should merge as-is.** It is correct within scope. The gap it does not solve is a separate, larger feature.

**2. Extend the `products` table with per-slot material code hint columns.** Add one `string` column per material slot storing the short code (or material name) that product type typically uses. These are human-readable TYPE codes, not FK references. They encode Level 2 of the two-level indirection.

**3. When a line item is created with a product selected, auto-resolve material FKs from the product's slot hints via the estimate's price book.** The resolution logic: for each slot hint on the product, look for an `estimate_materials` record in the current estimate whose `short_code` matches the hint (case-insensitive). If found, assign that `estimate_material.id` to the slot's `_material_id` on the line item. If not found, leave the slot null. This is the web equivalent of the Presets tab auto-fill.

**4. The slot hint columns store codes only — never prices, never FK references to library materials.** Price resolution always goes through `estimate_materials`. This preserves the two-level indirection exactly.

**5. This is a new spec (SPEC-029), not a revision of SPEC-022.** SPEC-022 is complete and merged. The Presets feature is a distinct data model addition and workflow change.

## Rationale

### Why not store FK references to library materials on products?

The Presets tab TYPE codes (`PULL1`, `HINGE1`) are job-scoped identifiers. On one job `PULL1` is a chrome pull; on another it is a brushed nickel pull — same code, different material. Storing a foreign key from `products.pulls_material_id → materials.id` would force a choice: either the product catalog stores a single global material (wrong — it varies by job), or the slot hints are FK references that get mapped per-estimate (adding a third level of indirection without benefit).

Storing short codes as strings on the product is correct. Resolution happens at estimate time, through the same `estimate_materials.short_code` matching that SPEC-022 already built.

### Why not extend the existing short code matching in SPEC-022?

SPEC-022 matches a code in the *description text* of a line item. The Presets feature matches a code on the *product definition* to a slot. These are different inputs. The SPEC-022 matcher is designed for CSV-imported descriptions. The Presets resolver is for product-catalog-driven slot assignment. They should be separate service objects because their inputs, triggers, and outputs are different, even though they share the resolution mechanism.

### Why not use JSONB to store per-slot hints on products?

Flat string columns per slot maintain the same structural consistency as the `_qty` columns already on `products`. Each slot is already a first-class citizen with its own column. Adding `exterior_slot_code`, `interior_slot_code`, etc., follows the existing pattern. JSONB adds type flexibility at the cost of column-level querying, schema clarity, and Rails attribute convenience methods. The number of slots is fixed (10). Flat columns are correct here.

### Why resolve at line item creation time, not lazily?

The Presets tab resolves at the moment Blake adds a product row. The web app should match this: when a line item is created with a product, apply the defaults immediately. Lazy resolution (resolve when saving the estimate, or when "apply" is clicked) would mean the user sees blank material slots that then silently fill — confusing. Eager resolution at creation is both consistent with the Excel model and what the estimator expects.

### Why is this SPEC-029 and not a revision of SPEC-022?

SPEC-022 is a closed spec on a merged PR. It correctly solved the short code auto-population problem for CSV import. Reopening or revising it would break the well-defined scope. The Presets feature requires a migration (new columns on `products`), a new service object, and new UI on the product form. These are distinct deliverables.

## Alternatives Considered

| Option | Pros | Cons | Rejected Because |
|--------|------|------|-----------------|
| FK references from `products` to `materials` for each slot | Referential integrity; no ambiguity | Product defaults would be global material choices, not job-specific codes; breaks job-specific pricing | Material selection is job-scoped; FK would force a single global default |
| JSONB `slot_codes` column on `products` | Flexible; one column | No per-column querying; schema opacity; inconsistent with existing flat slot columns | Flat columns are already the established pattern for this table |
| Extend SPEC-022's `LineItemAliasMatcherService` to handle Presets too | One service object | Different input (product slot codes vs description text), different trigger (create vs import/apply), different semantics; would muddle a clean service | Separate concerns; keep the services focused |
| Require the estimator to assign all material slots manually | Simpler app; no resolver needed | This is the very workflow problem the app is supposed to solve; the Presets tab is the core of Blake's 15-minute estimate capability | Violates the primary value proposition |
| Revise SPEC-022 to include Presets | Keep changes in one spec | SPEC-022 is closed; forces re-opening a merged PR; mixes two distinct features | Wrong scope boundary; risks destabilizing merged work |

---

## Consequences

### Positive

- The two-level indirection of the Excel model is fully represented in the data model. Level 1 = `estimate_materials.short_code`. Level 2 = `products.<slot>_slot_code`.
- Manually adding a line item by selecting a product auto-fills material slots from the estimate's price book, matching the Excel Presets tab behavior.
- Product defaults remain job-agnostic (codes, not prices). The system stays repricing-safe.
- The `Product#apply_to` service method extends cleanly to slot code resolution.
- SPEC-022 / PR 41 is unaffected and can merge immediately.

### Negative

- Ten new string columns on `products` (one per slot). This is a migration, but a simple one.
- The product form gains ten new fields for slot codes. This adds UI surface. The fields are optional, so existing products are unaffected.
- Slot code resolution at line item creation requires looking up `estimate_materials` by `short_code` — one additional query per line item creation (still O(1), not N+1, since the price book is small and loaded once).
- If the estimate has no `short_code` values set up, the resolver finds nothing and leaves all material slots null. This is the same state as today. No regression.

### Risks

| Risk | Mitigation |
|------|-----------|
| Product slot codes drift out of sync with estimate price book codes | The estimator already manages this in Excel; the UI should show unresolved slot codes as warnings on the line item form, similar to the "Needs review" badge in SPEC-022 |
| Estimator adds a line item before setting up short codes in the price book | Graceful degradation — slot resolution finds nothing, leaves material slots null, line item is saved with qty/labor defaults only; same as current behavior |
| Migration needed on a live app with products data | Migration is additive only (new nullable columns); no existing data is altered |
| `Product#apply_to` gets too complex | Extract slot resolution into `ProductSlotResolver.new(product, estimate).call` — a separate service that is injected into the controller action separately from `apply_to` |

## Proposed Data Model for SPEC-029

### `products` table additions

Add one `string` column per material slot, all nullable, default null:

| Column | Notes |
|--------|-------|
| `exterior_slot_code` | Short code for the exterior material (e.g., `"PL1"`, `"3/4\" MEL G2S"`) |
| `interior_slot_code` | Short code for the interior material |
| `interior2_slot_code` | Short code for the secondary interior material |
| `back_slot_code` | Short code for the back material |
| `banding_slot_code` | Short code for the banding material |
| `drawers_slot_code` | Short code for the drawer box material |
| `pulls_slot_code` | Short code for the pulls hardware (e.g., `"PULL1"`) |
| `hinges_slot_code` | Short code for the hinges hardware (e.g., `"HINGE1"`) |
| `slides_slot_code` | Short code for the drawer slides hardware (e.g., `"SLIDE1"`) |
| `locks_slot_code` | Short code for the locks hardware |

No index on these columns. Resolution is always scoped to one product at a time and done in Ruby.

### No changes to `estimate_materials`, `line_items`, or `estimates`

The resolution infrastructure already exists: `estimate_materials.short_code` (SPEC-022) and the nine `_material_id` FK columns on `line_items` (SPEC-014 / ADR-010).

### New service: `ProductSlotResolver`

```ruby
# app/services/product_slot_resolver.rb
#
# Resolves an estimate's price book short codes against a product's slot code
# hints, and assigns the matched estimate_material IDs to a line item.
#
# Usage:
#   ProductSlotResolver.new(product, estimate).call(line_item)
#
# Does not save. Caller is responsible for persisting the line item.
class ProductSlotResolver
  SLOT_MAP = {
    exterior:  :exterior_slot_code,
    interior:  :interior_slot_code,
    interior2: :interior2_slot_code,
    back:      :back_slot_code,
    banding:   :banding_slot_code,
    drawers:   :drawers_slot_code,
    pulls:     :pulls_slot_code,
    hinges:    :hinges_slot_code,
    slides:    :slides_slot_code,
  }.freeze

  def initialize(product, estimate)
    @product = product
    # Index by downcased short_code; blank codes are excluded.
    @code_index = estimate.estimate_materials
                          .where.not(short_code: [nil, ""])
                          .index_by { |em| em.short_code.downcase }
  end

  def call(line_item)
    return line_item if @code_index.empty?

    SLOT_MAP.each do |slot, code_attr|
      hint = @product.public_send(code_attr).to_s.strip.downcase
      next if hint.blank?

      matched = @code_index[hint]
      line_item.public_send(:"#{slot}_material_id=", matched&.id)
    end

    line_item
  end
end
```

**Deliberate design choices:**
- Exact match (not substring) — slot codes on products are precise; substring matching is for description text in SPEC-022.
- Builds an in-memory index once per resolve call — O(1) per slot lookup.
- Does not touch labor hours or quantities — `Product#apply_to` handles those.

### Controller integration

In `LineItemsController#create`, when `product_id` is present:

```ruby
product.apply_to(@line_item)                          # qty + labor defaults (existing)
ProductSlotResolver.new(product, @estimate).call(@line_item)  # material slot resolution (new)
@line_item.assign_attributes(line_item_params)        # estimator overrides take precedence
```

The order is intentional. `apply_to` runs first (quantities and labor hours). `ProductSlotResolver` runs second (material IDs). Estimator params run last (any explicit override wins). This matches the `apply_to` override convention already established in SPEC-013 / ADR-009.

## Recommended Implementation Sequence

1. **Merge PR 41 now.** SPEC-022 is complete and correct. It is independent of the Presets feature.

2. **Write SPEC-029 — Product Presets Auto-Population.** Scope: migration to add `<slot>_slot_code` columns to `products`; product form fields for slot codes; `ProductSlotResolver` service; controller integration in `LineItemsController#create`; "Unresolved slot" warning on the line item form for product-assigned line items where slot codes are set but no matching estimate_material was found.

3. **Do not add hardware auto-population to SPEC-022 or PR 41.** Hardware slots (pulls, hinges, slides) are part of the Presets feature, not the short code alias feature. The SPEC-022 decision to exclude hardware from alias matching is correct. Hardware slot codes belong in SPEC-029's `ProductSlotResolver`.

4. **Labor hour presets are already solved.** The `products` table already stores all labor hour columns and `Product#apply_to` already copies them. No additional work needed for labor hours.

## What SPEC-029 Should Cover

Required:
- Migration: ten `<slot>_slot_code` string columns on `products`, all nullable
- Product form: ten optional text inputs for slot codes, labeled clearly (e.g., "Exterior material code")
- `ProductSlotResolver` service with tests: exact code matching, partial price book (some codes missing), empty price book, overwrite by estimator params
- `LineItemsController#create`: call `ProductSlotResolver` after `apply_to` when product is present
- Request spec: create line item with product + price book codes → correct `_material_id` assignments
- System spec: add product with slot codes, create line item, verify material slots are pre-filled

Optional (can defer):
- "Unresolved slot" warning UI on the line item card when product slot codes exist but no match was found in the price book. This is the Presets-level equivalent of SPEC-022's "Needs review" badge.
- Bulk update of slot codes on existing products via import (low priority until catalog is populated)

Out of scope for SPEC-029:
- Changing SPEC-022 or the `LineItemAliasMatcherService` — those are finalized
- Per-estimate product presets (overriding product defaults per estimate) — not in the Excel model
- Labor hour presets — already implemented

## Open Questions for SPEC-029

| OQ | Question | Recommended Answer |
|----|----------|-------------------|
| OQ-A | Should slot codes on products use the exact short_code values from the estimate price book, or should they use the canonical material names from the library? | Short codes only. They are job-specific identifiers. Using library material names would require a cross-estimate lookup and would break the two-level indirection. |
| OQ-B | Should `ProductSlotResolver` warn the user when a slot code is set on the product but no matching short code is in the estimate's price book? | Yes, but as a UI concern, not a model validation. The resolver should return a list of unresolved slots alongside the line item so the controller can pass it to the view for display. |
| OQ-C | Should existing line items be re-resolved when the estimator edits short codes? | No — PR 41 already provides "Apply short codes" for re-resolving alias-matched items. Re-resolving product-slot-assigned items is a separate, rarer case. Defer or handle via a separate "Reset from product defaults" action. |
| OQ-D | Should banding be included in `ProductSlotResolver`? | Yes. Banding has a `banding_material_id` FK on `line_items` and a `banding_slot_code` on products. The resolver should handle it even though banding has no qty column. |
